# 第一章 项目介绍

## 1.1 项目背景与选题

外卖订单履约是一条典型的**长链路业务**：一次下单要经过校验、计价、优惠、支付、派单、配送、结算、统计等多个环节，每个环节的规则都独立变化（商家起送价不同、优惠券规则由运营配置、支付渠道接口各异、派单策略随运力调整）。

如果把这些变化都写成 `if-else`，代码会迅速腐化；因此本项目的选题定位是：

> **用一个真实业务闭环，把 GoF 的 23 个设计模式中可落地的 19 个「用出来」，并同时交付一个可独立运行、可单独学习的设计模式实例库。**

项目包含两个层次：

| 层次 | 模块 | 定位 |
| --- | --- | --- |
| 设计模式实例库 | `patterns` | 17 个可独立运行的 Demo，覆盖 19 个设计模式，每个 Demo 都有 `main` 方法 |
| 综合业务系统 | `delivery-platform` | 外卖订单履约平台，把设计模式组合起来跑通完整业务闭环 |

## 1.2 技术栈

| 类别 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | **Java 17** | 使用 `record`（不可变值对象）、`sealed`/`switch` 表达式、`List.of`、文本块等新特性 |
| 构建 | **Maven 多模块** | 父工程统一管理 JDK 版本、UTF-8 编码、依赖与插件版本 |
| 测试 | **JUnit 5**（5.10.2） | 8 个测试类、**91 个用例**，全部通过 |
| 建模 | **PlantUML** | 核心类图 1 张、时序图 2 张 |
| 依赖 | **零第三方运行时依赖** | 只用 JDK 标准库；JUnit 仅测试作用域 |
| 界面 | **控制台（CLI）** | 交互式菜单 + 一键自动演示脚本 |
| 数据存储 | **内存实现**（单例仓储） | 通过端口（接口）隔离，可替换为文件/数据库 |

**为什么坚持零第三方依赖**：课程作业要展示的是设计模式本身的实现细节。例如优惠券规则解释器完全手写（词法分析 → 递归下降语法分析 → AST 求值），而不是引入 Aviator/QLExpress——否则最核心的知识点就被藏进第三方库里了。

# 第二章 设计

## 2.1 分层架构设计

项目采用**四层 + 两模块**的结构，核心原则是「**依赖单向、领域纯净**」：

```text
┌─────────────────────────────────────────────────────────────┐
│  ui 层         ConsoleUI（控制台菜单，只调用门面）             │
├─────────────────────────────────────────────────────────────┤
│  app 层        DeliveryPlatformApplication（入口）            │
│  bootstrap 层  PlatformBootstrap（组合根）/ DemoRunner        │
├─────────────────────────────────────────────────────────────┤
│  application   OrderFacade（外观）│ DispatchCenter（中介者）  │
│                OrderMemoManager   │ InventoryService（单例）  │
│                validator/*（职责链）│ report/*（访问者）        │
├─────────────────────────────────────────────────────────────┤
│  domain        订单聚合 + 参与方 + 端口（完全无外部依赖）      │
├─────────────────────────────────────────────────────────────┤
│  infrastructure 仓储（单例）│ 支付适配器 │ 解释器 │ 事件监听器 │
└─────────────────────────────────────────────────────────────┘
```

**关键设计决策：**

1. **领域层不依赖任何设计模式实现**。`domain` 包里只有订单聚合、值对象和端口接口（`OrderStore`、`CouponEvaluator`、`PaymentGateway`、`DispatchStrategy`）；解释器、适配器、监听器的实现全部在 `infrastructure`。因此领域逻辑可以在没有控制台、没有网络的情况下被单元测试完整覆盖。
2. **视图与业务分离**。`System.out` 与输入解析只出现在 `ui` 包，业务层不打印任何东西。
3. **单例只用于真正的全局资源**：仓储、库存服务、支付网关注册表、平台配置。

## 2.2 核心类图说明

> 完整类图见 `docs/uml/01-核心类图.puml`（用 IDEA/VSCode 的 PlantUML 插件渲染后插入此处）。
>
> **【截图占位 1】** 在此处插入「核心类图」渲染图。

类图按包分为 6 个区域，阅读顺序建议如下：

### （1）`domain.order`：订单聚合（图的中心）

| 类 | 角色 | 设计要点 |
| --- | --- | --- |
| `Order` | **聚合根** | 唯一的订单入口。所有状态变更必须走 `transitionTo()`，外部无法直接 `set` 状态 |
| `OrderStatus` | 状态枚举 + **迁移矩阵** | 在枚举静态块里定义「谁能走到谁」，非法流转只有一处判断（`canTransferTo`） |
| `OrderState` + 7 个内部状态类 | **状态模式** | `OrderStatus` 是「数据」，`OrderState` 是「行为」；每个状态只覆盖自己允许的操作，其余一律 `reject()` |
| `OrderItem` | **值对象（record）** | 下单时"锁价"快照，同名菜品自动合并，天然不可变 |
| `OrderSnapshot` | **备忘录（Memento）** | 覆盖订单**全部可变状态**（含 5 个时间戳与取消原因） |
| `OrderVisitor<R>` | **访问者（Visitor）** | `accept()` 提供双分派入口，报表/导出/审计都从这里扩展 |
| `OrderRepository` / `OrderService` | **端口（Port）** | 领域层只定义契约，实现放在基础设施层 |

**关系要点：**
- `Order ◆── OrderItem`：组合（聚合内部元素，生命周期一致）
- `Order ── OrderStatus`：关联（当前状态）
- `Order ⇢ OrderState`：依赖（行为委托，不持有）
- `Order ⇢ OrderSnapshot`：生成/恢复（双向）
- `Merchant ◆── Dish`：组合（菜单）

### （2）`application`：应用编排层

| 类 | 角色 | 设计要点 |
| --- | --- | --- |
| `OrderFacade` | **外观（Facade）** | 业务闭环编排中心。一条 `submit()` 内部完成「校验链 → 计价 → 优惠 → 库存预占 → 落库 → 发事件」 |
| `OrderValidator` + 6 个子类 | **职责链（Chain）** | 非空 → 起送价 → 库存 → 地址 → 频控 → 风控；**排序原则：先廉价后昂贵**；`collectTrace()` 让"卡在第几环"可见 |
| `DispatchCenter` | **中介者（Mediator）** | 订单、商家、骑手互不引用，全部经派单中心转发（星形拓扑） |
| `OrderMemoManager` | **备忘录 Caretaker** | 只负责存取快照，**绝不窥探内容** |
| `ReportVisitor` | **访问者 ConcreteVisitor** | 营业额、客单价、销量榜、骑手榜、大额订单统计 |
| `InventoryService` | **单例 + 命令接收者** | 预占/回滚库存，支持整单原子性 |

### （3）`domain.support`：策略与端口

- `PricingStrategy` + `PricingContext`：**策略模式**（配送费：基础阶梯价/会员免运费/雨天 1.5 倍/高峰 +2）
- `DispatchStrategies`：**策略模式**（最近优先/最少负载/评分最高）
- `PaymentGateway`：**适配器模式的 Target 接口**
- `CouponEvaluator`：**解释器模式的边界接口**
- `DomainEventPublisher` + `OrderEventListener` + `OrderEvent`：**观察者模式三件套**

### （4）`infrastructure`：实现层

- `CouponRuleInterpreter` + `CouponExpression`（8 个表达式节点）+ `CouponRuleParser`：**解释器模式完整实现**
- `WalletPaymentAdapter` / `WechatPaymentAdapter` / `AlipayPaymentAdapter` / `BankCardPaymentAdapter`：**适配器模式**
- `PaymentGatewayRegistry`：注册表 + 单例
- `InMemoryOrderStore` / `InMemoryActorStore`：**单例 + 模板方法**
- `OrderEventListeners`（5 个监听器）：**观察者模式**

> 完整时序图见 `docs/uml/02-下单时序图.puml`。
>
> **【截图占位 2】** 在此处插入「下单时序图」渲染图。

时序图按**五个阶段**推进，每个阶段对应一到两个设计模式：

| 阶段 | 交互序列 | 体现的模式 | 讲解要点 |
| --- | --- | --- | --- |
| ① 选择商品与构建订单 | `UI → Facade.create()` → `Store` 取用户商家 → `OrderBuilder.build()` | **建造者** | `build()` 内统一校验不变量（必填项非空、明细必须同商家）；`addDish` 循环里同名菜品自动合并 |
| ② 提交订单 → 校验链 | `Facade → ValidatorChainFactory.defaultChain()` → 6 环逐个 `check()` | **职责链** | 每环返回「通过/否决原因」；被否决时抛 `OrderValidationException` 并在 `finally` 里收集轨迹；命中顺序：订单非空 → 起送价 → 库存 → 地址 → 频控 → 风控 |
| ③ 计价策略 + 优惠券解释 | `Facade → PricingContext.deliveryFeeFor()` → `CouponRuleInterpreter.evaluateCoupon()` | **策略 + 解释器** | 策略按「会员 > 雨天 > 高峰 > 基础」优先级自动选；解释器把 `满30减5` 解析成 AST 后求值，并做「非负 + 不超过小计」封顶 |
| ④ 库存预占 + 状态流转 | `Facade → InventoryService.reserveAll()` → `Order.submit()` → `transitionTo(PENDING_PAYMENT)` | **状态 + 单例** | 库存预占是"两阶段"语义：任一菜品不足则回滚已预占部分，避免库存被慢慢吃掉 |
| ⑤ 落库 + 事件通知 | `Facade → Store.save()` → `Publisher.publishFor()` → 5 个 `Listeners.onEvent()` | **观察者** | 发布者只广播，不知道谁在听；遍历订阅者**快照副本**以免回调中退订引发并发修改异常；单个监听器异常被隔离 |

**特别说明（讲解亮点）**：校验链被否决时会抛异常中断流程，但**轨迹仍然完整**——这是用 `try/finally` 收集的，因此控制台能打印出"前一环通过了、卡在第几环"。这是实际开发中发现并修复的缺陷。

> 完整时序图见 `docs/uml/03-派单时序图.puml`。

时序图按**六个阶段**推进：

| 阶段 | 交互序列 | 体现的模式 | 讲解要点 |
| --- | --- | --- | --- |

| ② 骑手调度 | `Center → Strategy.pick(candidates, order)` 循环尝试 | **策略 + 回退降级** | 首选策略选不出人时，按回退链依次降级（最近 → 最少负载 → 评分最高），全过程记录轨迹 |

| ④ 取餐与送达 | `Facade.startDelivery()` → `memoManager.backup()` → `OrderState.startDelivery()`；`complete()` 时释放骑手负载 | **状态 + 备忘录 + 观察者** | 关键操作前自动记快照；送达后骑手负载 -1，为 0 则回到空闲 |
| ⑤ 可选撤销 | `Facade.undo()` → `memoManager.undo()` → `Order.restore(snapshot)` | **备忘录** | 整体状态替换，而非逐字段逆向操作 |
| ⑥ 归档与报表 | `Store.archiveBefore()` → `ReportVisitor` 遍历 | **模板方法 + 访问者** | 归档流程骨架固定（筛选 → 终态判定 → archive），存储介质可换；报表用双分派外置 |

**特别说明（讲解亮点）**：`DispatchOutcome` 是专门定义的结果对象，而不是 `boolean`——因为「无运力」应该进重试队列、「状态不对」重试没有意义、「策略选不出」要考虑放宽策略，这三类失败的处理方式完全不同。

## 3.2 重点模式实现说明

### 3.2.1 解释器模式（本项目最复杂的模式）

**要解决的问题**：运营希望「改优惠规则不改代码、不发版」。

**实现分三步：**

**第一步 · 定义文法（支持的小语言）**

```text
expr      := orExpr
orExpr    := andExpr (("或" | "||") andExpr)*
andExpr   := primary (("且" | "并且" | "&&") primary)*
primary   := "(" expr ")" | condition
condition := "满" NUM "减" NUM                    ← 满减
           | ("打" NUM "折") | (NUM "折")         ← 折扣
           | "会员等级" CMP NUM                   ← 等级比较（NORMAL=0/GOLD=1/DIAMOND=2）
           | "小计" CMP NUM                       ← 小计比较
CMP       := ">=" | "<=" | "==" | ">" | "<"
```

**第二步 · 递归下降解析成 AST**

`CouponRuleParser` 里每条产生式对应一个方法，**运算符优先级由调用层次决定**：
`parseOr()` → `parseAnd()` → `parsePrimary()`。例如：

```text
输入：(满30减5 或 满50减10) 且 会员等级==2
解析树：
  And（且）:
    ├─ Or（或）:
    │    ├─ FullReduction（满减）: 满30减5
    │    └─ FullReduction（满减）: 满50减10
    └─ Compare（比较）: 会员等级==2
```

**第三步 · 表达式节点求值**

关键设计是**把「求值」与「求优惠」分开**：

```java
public abstract class CouponExpression {
    public BigDecimal value(CouponContext ctx)      // 求「值」：数字返回自身、会员等级返回序号、小计返回金额
    public abstract BigDecimal contribute(ctx)      // 求「优惠贡献」：条件节点返回 0，金额节点返回抵扣额
}
```

**为什么必须分开**：如果所有节点都返回 `BigDecimal`，那么「等级 1」与「优惠 1 元」在组合子（且/或）里无法区分。分开之后，「且」的实现就变得极其简单：两侧都"满足"才生效，生效时取非零那一侧的金额。

**为什么自研而不用第三方**：课程要展示解释器模式本身的实现细节（词法 → 语法 → AST → 求值）。生产系统反而更可能用 Aviator/QLExpress，这是刻意的权衡取舍。

**容错性**：非法规则给出带位置的中文错误，而不是崩溃：

```text
「满30减」→ 优惠券规则解析失败（第 4 个字符附近）：缺少关键字「减」…
```

### 3.2.2 状态模式

**问题**：订单有 7 个状态、6 个操作，若用 `switch (status)` 判断，这些分支会散落在订单服务、控制台、报表等多处，每加一个状态就要改所有 `switch`。

**实现**：拆成「数据」与「行为」两层。

```java
// 数据层：OrderStatus 枚举 + 迁移矩阵（谁能走到谁）
TRANSITIONS.put(DRAFT, EnumSet.of(PENDING_PAYMENT, CANCELLED));
TRANSITIONS.put(DELIVERING, EnumSet.of(COMPLETED));   // 配送中不能取消

// 行为层：OrderState 抽象类，默认全部拒绝，子类只覆盖自己允许的操作
public abstract class OrderState {
    public void submit(Order order)  { reject(order, "提交"); }   // 默认拒绝
    public void cancel(Order order, String reason) { reject(order, "取消"); }
    protected void reject(Order order, String operation) {
        throw new IllegalOrderStateException(order.orderId(), status(), status(),
            String.format("当前状态[%s]不允许执行「%s」操作；本状态允许的操作：%s",
                name(), operation, allowedOperations()));   // 白名单式提示
    }
}
```

**效果**：`DraftState` 只覆盖 `submit`/`cancel`，`DeliveringState` 只覆盖 `complete`，两个终态一个都不覆盖。异常信息自带「本状态允许的操作」，控制台提示非常友好。

### 3.2.3 职责链模式

**六环的顺序不是随意排的，而是按「先廉价后昂贵」**：

```java
OrderValidator head = new EmptyOrderValidator();          // 零成本：只看集合是否为空
head.setNext(new MinimumAmountValidator());               // 一次金额比较
head.next.setNext(new StockValidator(inventory));         // 需要查库存（可能有 IO）
head.next.next.setNext(new AddressValidator());           // 需要读地址/未来接地图服务
head.next.next.next.setNext(new FrequencyLimitValidator());// 需要查频控计数
head.next.next.next.next.setNext(new RiskControlValidator());// 最重，聚合前面所有结论才执行
```

**实现细节（容易踩坑）**：`setNext()` 返回**链头**而不是参数。若返回 `next`，`a.setNext(b).setNext(c)` 的语义就依赖返回值，极容易误用（实测会导致链上只剩 2 个处理者）。

**轨迹收集**：校验失败会抛异常，因此必须用 `try/finally` 汇总轨迹：

```java
try {
    chain.validate(context);
} finally {
    this.lastValidationTrace = chain.collectTrace();   // 即使被拦下，也能打印完整过程
}
```

### 3.2.4 适配器模式

**四个渠道的真实差异**（这正是适配器要吸收的「变化点」）：

| 渠道 | 第三方接口签名 | 单位 | 成功判定 | 适配器要做的事 |
| --- | --- | --- | --- | --- |
| 微信 | `unifiedOrder(outTradeNo, totalFen)` → `Map` 报文 | 分 | `return_code == "SUCCESS"` | 元→分、解析报文、提取流水号 |
| 支付宝 | `trade(subject, outBizNo, yuan)` → `String` | 元 | `"TRADE_SUCCESS"` | 补默认标题、字符串→布尔 |
| 银行卡 | `debit(accountRef, amountInCent)` → `int` | 分 | `code == 0` | 元→分、**错误码字典翻译**成中文原因 |
| 余额 | 平台自身账户 | 元 | 余额充足 | 扣款并回写新用户对象（record 不可变） |

**统一契约**：

```java
public interface PaymentGateway {
    String channel();
    Payment pay(String orderId, BigDecimal amount, String payerRef);   // 永远返回 Payment，不抛异常
    default boolean supports(BigDecimal amount, String payerRef) { return true; }
}
```

**为什么用对象适配器（组合）而不是类适配器（继承）**：Java 单继承，继承会占掉唯一的继承位并暴露第三方全部方法；组合只暴露翻译后的能力，且 SDK 升级的影响被限制在适配器内部。

**为什么余额支付也写成适配器**：如果余额支付"特殊处理"，订单服务里立刻会出现「本地渠道一个分支、第三方渠道另一个分支」，适配器的价值就被抵消了。

### 3.2.5 中介者模式

**不用中介者**：订单要认识骑手池、骑手要知道订单、商家要通知骑手 → 3 组关系、6 条双向链路。
**用中介者**：三方都只与派单中心通信 → 3 条链路（星形拓扑）。

**中心自身的职责极力克制**，只做三件事：
1. 判断订单能否派（前置校验）；
2. 委托策略挑选骑手（自己不写排序逻辑）；
3. 促成绑定并发布事件。

**多策略回退降级**（真实派单系统的常见做法）：首选策略选不出人时，按回退链依次尝试，并记录完整轨迹：

```text
· 候选骑手 2 名：[李骑手(空闲, 负载 0/3, 距离 1.20 km), 赵骑手(空闲, 负载 0/3, 距离 0.80 km)]
· 策略[最近优先]（按骑手与商家的距离升序，取最近者）选中骑手 赵骑手(负载 0/3, 距离 0.80 km)
· 骑手[赵骑手]负载更新：0/3 → 1/3
```

### 3.2.6 观察者模式

**五个订阅者、各取所需**：

| 监听器 | 关心的事件 |
| --- | --- |
| `UserSmsListener` | 提交/支付/派单/送达/取消（生成用户短信文本） |
| `MerchantPortalListener` | 新订单/已支付/已取消/派单失败 |
| `RiderAppListener` | 派单/取餐/送达 |
| `ReportListener` | 全部事件（按类型计数，供实时报表口径） |
| `AuditLogListener` | 全部事件（完整留痕，合规要求） |

**两个工程细节：**
1. **遍历订阅者快照副本**：避免监听器在回调里 `unsubscribe` 导致 `ConcurrentModificationException`；
2. **异常隔离**：单个监听器抛异常只记录日志，不影响其他订阅者，更不能拖垮下单主流程。

### 3.2.7 备忘录模式

**核心设计决定：快照必须覆盖订单的全部可变状态。**

早期实现只快照"业务子集"（状态、明细、金额），结果测试暴露了一个真实缺陷：撤销之后 `cancelReason` 仍然残留——状态回退到待支付，但取消痕迹还在，快照不再是「某一时刻的完整状态」。

修正后 `OrderSnapshot` 包含 17 个字段（含 5 个时间戳与取消原因），`restore()` 做**整体替换**而非逐字段逆向。这正是备忘录模式区别于命令模式撤销的地方：**备忘录保存"对象状态"，命令保存"操作"**。

**职责边界**：`OrderMemoManager`（Caretaker）只负责存取快照，`historyOf()` 只暴露描述、**绝不暴露快照内部数据**。

### 3.2.8 访问者模式

**为什么统计报表要从订单里搬出来**：报表指标（营业额、客单价、菜品销量榜、骑手接单榜、大额订单占比）有三个特征——变化频繁、与订单自身状态流转无关、需要跨订单聚合。写进 `Order` 会让聚合越来越胖。

**实现**：订单只留一个双分派入口

```java
public <R> R accept(OrderVisitor<R> visitor) { return visitor.visit(this); }
```

`ReportVisitor` 实现累加逻辑，`toReport()` 产出不可变的 `StatisticsReport`。新增一个指标 = 新增一个 Visitor，**订单类一行都不用改**。

**代价也写进了注释**：新增一种订单类型需要改动所有 Visitor。本项目订单类型稳定，因此收益大于成本。

### 3.2.9 其余模式实现要点速览

| 模式 | 实现要点 |
| --- | --- |
| **单例** | 仓储用饿汉式（类加载即创建，语义简单且线程安全）；Demo 里对比了双检锁/静态内部类/枚举三种写法；8 线程并发生成 1600 个订单号零重复 |

## 3.3 开发中发现并修复的真实缺陷

这部分最能体现"设计模式不是画出来好看，而是真能暴露问题"：

| # | 缺陷 | 症状 | 修复 |
| --- | --- | --- | --- |
| 1 | **备忘录快照不完整** | 撤销后 `cancelReason` 残留，状态回退但痕迹还在 | 快照扩展为全部 17 个可变字段，`restore()` 整体替换 |
| 2 | **库存只回滚不扣减** | 取消订单后库存反而变多（越取消越多） | 提交订单即预占库存（含失败回滚），取消时回滚 |
| 3 | **校验轨迹丢失** | 校验链一票否决抛异常后轨迹为空，无法定位卡在哪一环 | 用 `try/finally` 收集轨迹 |
| 4 | **职责链 `setNext` 返回语义** | 返回 `next` 时链式写法歧义，实测链上只剩 2 个处理者 | 改为返回链头，语义唯一 |
| 5 | **策略模式被架空** | `PricingContext` 每次计价都重跑自动选择，运营手工设置的策略被静默覆盖 | 引入 `strategyOverridden` 标记，显式设置优先，`useAutoSelection()` 交还选择权 |

- **功能**：12 个履约环节全部跑通，含 5 类异常场景（校验拦截、余额不足、运力枯竭、非法状态流转、取消回滚）验证。

## 附：答辩常见提问准备

| 可能的提问 | 回答要点 |
| --- | --- |
| 为什么用解释器模式而不是直接存"满30减5"的字段？ | 规则要可组合（且/或/括号/等级判断），字段无法表达组合；且运营改规则不应改代码。 |
| 快照里为什么要放时间戳？ | 备忘录语义要求"完整状态"，只回滚一部分会出现"状态回去了、痕迹没回去"的中间态（我们实际踩过这个坑）。 |
| 状态模式和迁移矩阵为什么并存？ | 矩阵管"能不能走"（数据），状态类管"这个状态下允许做什么"（行为）。职责不同，都是必要的。 |
| 访问者模式的代价是什么？ | 新增元素类型要改所有 Visitor；本项目订单类型稳定，所以收益大于成本。 |
| 中介者会不会变成上帝类？ | 会，所以我们把"怎么挑骑手"外置成策略、"通知谁"外置成观察者，中介者只保留"协调 + 前置校验 + 绑定"。 |
| 为什么没有用 Spring？ | 课程要考察的是设计模式与架构分层本身；Spring 的依赖注入会掩盖"组合根如何装配"这一学习点。我们用 `PlatformBootstrap` 手工装配，逻辑完全可见。 |
| 库存为什么在提交时预占而不是支付后扣？ | 避免超卖。代价是未支付订单会占用库存，真实系统需要"超时释放"定时任务——这是可以继续改进的点。 |
